# Шифрование текстов Nyan message

Используется AES-256-GCM из `cryptography`: ключ 32 байта, новый случайный nonce 12 байт
для каждого шифрования, проверка целостности 128-битным тегом GCM. Контекст поля включён
в аутентифицируемые данные: перенос ciphertext из текста в подпись не проходит проверку.
Fernet здесь не используется: он основан на AES-128, несмотря на 32-байтовый ключ.

## Что хранится

Структура SQL-таблиц, остальные колонки, ключи и связи не меняются.
Внутри прежнего JSON в `messages.data` зашифрованы `text`, `caption`, `details`.
`None` остаётся `None`; пустая строка тоже шифруется. Значения содержат объект
с `$encrypted`, версией, идентификатором ключа, nonce, ciphertext и тегом сравнения.
Сам ключ никогда не попадает в БД, код, журнал или архив обновления.

`outbox.data` также защищён: копии `old/new` шифруются так же, а готовый текст уведомления
шифруется отдельно. ID, получатель, счётчики попыток и прогресс отправки остаются прежними.
Иначе удалённые тексты снова появлялись бы открытыми в очереди уведомлений.

`save_message()` шифрует копию записи, не меняя исходный объект обработчика.
`load_message()` возвращает зашифрованные поля и проверяет формат/идентификатор ключа.
Сравнение правок работает через отдельный HMAC от текста, nonce и имени поля. Сам текст
для сравнения не открывается, неизменённый повтор не создаёт лишнего уведомления.
`send_notification()` открывает поля непосредственно перед отправкой; перед этим
очередь проверяет действующий доступ получателя. Неверный ключ или повреждённый ciphertext
не превращаются в текст уведомления и не приводят к записи открытого текста.

## Статистика без расшифровки сообщений

В том же JSON добавлен `_encrypted_stats`: зашифрованный расчётный снимок длины,
счётчиков слов и существующего SHA-256-отпечатка содержания. При сохранении он рассчитывается
из доступного входящего сообщения. При миграции из открытой старой записи.

Восстановление статистики и события читают только этот снимок. Поля текста, подписи
и деталей не расшифровываются для аналитики. Формулы подсчёта, фильтр стоп-слов, авторы,
временные интервалы, идентификаторы событий и первичные ключи остаются прежними.
Это поддерживает и историю, которую бот ещё не успел агрегировать.

**Это шифрование содержания сообщений, а не всей SQLite-базы.** Имена/ID, метаданные,
готовые агрегаты и частые слова в прежних таблицах статистики остаются в прежнем виде.
Тексты нужны в памяти во время получения сообщения и отправки уведомления.

## Ключ

Обязательная настройка `MESSAGE_ENCRYPTION_KEY` читается непосредственно из `.env`
рядом с `app.py`. Переменная процесса с таким именем не заменяет файл; интерполяция
dotenv отключена. В коде нет запасного ключа и режима записи текста без шифрования.
При отсутствии/неверном ключе бот останавливается с понятной ошибкой до работы с данными.
Если идентификаторы ключей в старых строках не совпадают, запуск также запрещён.

Создание:

```sh
pip install -r requirements.txt
python generate_encryption_key.py
```

Скрипт сам добавляет случайный ключ в `.env`, не печатая его. Существующий ключ
не заменяет. На Linux новый `.env` имеет режим 0600. `.env` нужно сохранить отдельно
в защищённом месте: при потере ключа не получится открыть сообщения и резервные копии.
Не создавайте новый ключ при обычном обновлении или переустановке бота.
Ротация ключа в эту задачу не входит.

## Одноразовая миграция

Остановите бота и другие программы, пишущие в эту базу. Сначала проверьте:

```sh
python migrate_message_texts.py
```

Применение:

```sh
python migrate_message_texts.py --apply --bot-stopped
```

База берётся из `DB_PATH` в `.env`, относительно директории этого файла; можно явно
указать `--db /path/messages.sqlite3`. Несуществующая база не создаётся автоматически.
Миграция проверяет SQLite и все строки, их форматы и аутентичность уже зашифрованных полей.
Маркер сам по себе не считается доказательством корректного шифрования.

Перед записью создаётся согласованная SQLite-копия, включающая WAL. Она шифруется потоково
в `encryption_backups/*.sqlite3.aes`, проверяется обратным чтением и SHA-256 без вывода
содержимого. Временная открытая копия имеет режим 0600 и удаляется в `finally`.
Директория резервных копий создаётся с режимом 0700. Если процесс насильно прерван
в момент создания копии, в ней может остаться скрытый временный `.snapshot-*` файл;
после проверки результата его следует удалить. Старые резервные копии других версий
автоматически не изменяются и могут содержать открытый текст.

Обновляются только `messages.data` и `outbox.data`, порциями до 250 строк внутри одной
транзакции. При ошибке до commit изменения отменяются. SQL-схема, ROWID, created_at,
индексы, данные статистики и прогресс уведомлений сохраняются.
Повторный запуск пропускает корректные зашифрованные строки без повторного шифрования.

Включается `secure_delete` для перезаписи освобождённых SQLite-ячеек; после commit WAL
очищается через checkpoint TRUNCATE. VACUUM намеренно не выполняется: он может изменить
неявные ROWID, на которых основан прогресс восстановления статистики.
Ошибка очистки WAL после commit означает, что шифрование уже выполнено, но нужно закрыть
чужие подключения и повторить миграцию для завершения очистки. На уровне ОС/SSD это
не является гарантией уничтожения всех прежних копий данных.

## Панель Pterodactyl без терминала

1. Нажмите Stop, загрузите и распакуйте архив обновления в корень проекта.
2. В Startup найдите PY_FILE / файл запуска Python. Временно замените `app.py` на
   `prepare_encrypted_storage.py` и нажмите Start.
3. requirements установятся обычным способом панели. Скрипт создаст ключ в `.env`
   (или сохранит уже существующий), выполнит миграцию с резервной копией и завершится.
4. Дождитесь строки «Подготовка завершена». Завершение этого одноразового скрипта нормально.
   Если есть ошибка, оставьте бота остановленным и сохраните лог; не меняйте ключ.
5. Верните PY_FILE=`app.py` и нажмите Start. Ключ из `.env` сохраните в защищённом месте.

Не запускайте подготовительный скрипт одновременно с работающим ботом.

## Восстановление копии

```sh
python migrate_message_texts.py --restore-backup encryption_backups/example.sqlite3.aes --output restored.sqlite3
```

Создаётся новый файл, рабочая база не заменяется. Существующий выходной файл не перезаписывается.
При неправильном ключе/повреждении незавершённый результат удаляется. Восстановленная
копия содержит прежние открытые тексты; используйте её только для контролируемого отката.
Откат выполняется при остановленном боте после проверки новой копии.
